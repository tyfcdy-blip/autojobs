# 自动化脚本接入与编写规范草案

版本：v0.1。日期：2026-11-19（Asia/Shanghai）。适用对象：自动化脚本维护人员、中台及执行端开发人员。

本规范用于把现有 Python 自动化脚本接入统一中台：任务在指定电脑和环境中单次执行，由脚本判定业务结果，中台保存执行记录并统一告警。当前已实现 M0 本机执行端及标准库结果写入工具，具体可用字段、大小限制、环境变量和命令见 [执行端 README](../../apps/agent/README.md)。云端中台和通知尚未实现；下文最初的建议仍保留其评审语境，不据此假定所有接入能力已经完成。

## 1 已确认的接入要求

- 中台部署在阿里云 Linux 服务器，通过 Docker 部署；执行端位于专用 Windows 10 电脑。任务固定绑定执行电脑，同一电脑一次只执行一个任务。
- 中台上传并分发脚本及依赖清单，统一设置执行时间。现有内部定时如何改造属于接入方案，第 3 节给出单次入口的建议。
- 运行前检查指定 Python、虚拟环境、依赖包和浏览器环境；先展示缺项，由使用者点击准备环境。自动补齐的具体组件范围尚待确定。
- 固定业务参数和本地文件路径可以继续在脚本中配置，第一版不要求临时传参或在线上传业务输入文件。
- 脚本按照统一约定返回成功或失败及结果值。失败结果由中台接收、保存并发送至钉钉；成功通知默认关闭，可按任务开启。
- 步骤上报可选，不要求百分比进度。未上报步骤的脚本仍应能展示基本执行状态。
- 支持立即运行、暂停后续定时、取消排队和停止运行。排队超时取消本轮并通知；最长运行时间默认 24 小时，可按任务设置，超过后终止本轮并告警。

以下第 2 至第 8 节为满足上述要求的**建议接入约定**。字段名、传输通道、包格式和错误码尚未冻结，应在接口设计及接入验证后确定，不得把示例当作已实现接口。

## 2 提交脚本时需要提供的内容

| 内容 | 维护人员需说明什么 | 执行前检查目标 |
| --- | --- | --- |
| 脚本及版本 | 单次执行入口、必要模块、版本标识 | 分发内容完整，运行版本可追溯 |
| Python 要求 | 支持的版本、是否使用指定虚拟环境 | 解析到目标电脑上的明确解释器，不使用模糊的默认 Python |
| 依赖清单 | 所需包及适用版本约束，可提供 requirements.txt | 在该任务选定的环境内检查，不以其他环境已安装为依据 |
| 浏览器要求 | 使用的自动化工具、浏览器及组件要求、启动或连接方式 | 指定组件存在且可用；无法检查的项目显示未验证 |
| 工作目录和本地文件 | 固定配置位置、必要输入文件、输出目录 | 路径、读取和写入条件符合任务要求 |
| 业务完成条件 | 成功标准、失败结果、部分完成如何判定 | 不把“进程没有报错”直接等同于业务成功 |
| 重跑与清理说明 | 重复执行影响、已产生结果如何处理、可清理资源 | 人工决定重跑前能判断是否会重复产生副作用 |

任务包可采用包含入口、模块、依赖清单及说明的归档文件，具体格式和目录布局待设计。不要把虚拟环境目录、真实凭据、浏览器完整用户资料或生产数据打进任务包。电脑上的解释器路径与登录状态由执行环境管理，不应复制进通用脚本包。

环境检查以任务声明为依据，不能承诺通过分析源码识别全部隐含依赖。自动安装前应展示目标环境、缺项和预期变更；不擅自升级其他任务共享的环境。Python 本体、系统软件和浏览器组件的自动安装边界需分别确认。

## 3 单次执行与结果交付

建议的一次执行过程为：执行端确认任务版本和环境 → 分配并传入本轮标识 → 启动单次入口 → 脚本执行并可选上报步骤 → 脚本提交最终结果 → 完成本轮资源清理并退出 → 执行端结合结果与退出情况确认终态。

- 每轮由中台或执行端提供唯一 `run_id`，脚本沿用该标识，不自行生成另一轮标识。具体传入方式待设计。
- 单次入口完成后退出，不在内部等待下一次定时，不再自行启动另一个常驻调度循环。接入切换时先停用原定时入口，再启用中台计划。
- 最终结果通过专用结构化通道交付。通道可在技术设计中选择受控结果文件或进程通信等方式，当前不指定文件路径、环境变量名或请求地址。
- 日常日志与最终结果分开；不能把任意控制台输出、最后一行文字或 Python 函数的内存返回值直接当作中台已收到的结果。
- 每轮提交一个逻辑最终结果。断线重传是同一结果的重复交付，不是重新运行脚本；收到确认前的缓存、确认和清理由执行端统一处理。
- 任务尚未启动时发生的环境或分发失败，由执行端生成平台诊断，不伪装成脚本返回的业务失败。

## 4 最终结果建议结构

建议采用 UTF-8 JSON。下列字段用于沟通契约，尚不是正式接口定义；长度、容量、支持版本及校验细则需在协议设计中补齐。

| 字段 | 建议类型 | 约束与含义 |
| --- | --- | --- |
| `protocol_version` | 字符串 | 必填；示例为 `0.1`，用于识别契约版本，不能由接收端默默忽略不支持的版本 |
| `run_id` | 字符串 | 必填；必须与本次实际执行记录一致，不能串入其他轮次 |
| `status` | 字符串 | 必填；脚本业务结果仅使用 `success` 或 `failed` |
| `message` | 字符串 | 必填、非空；人能读懂的结果说明；失败时说明原因，避免只写“错误” |
| `result` | JSON 值 | 必填，允许对象、数组、字符串、数字、布尔值或 `null`；承载脚本约定的返回值 |
| `error` | 对象或 `null` | 可选；诊断信息，例如 `code` 与已脱敏的 `details`；不能替代 `status` |

`result` 的业务结构由各脚本说明，中台不得强制要求“入库条数”或固定数据库成功标志。内容必须可以合法序列化，不接受 Python 对象、文件句柄、二进制内容、NaN 或 Infinity。金额、日期等需要明确表达方式，不依赖隐式类型转换。

成功示例仅说明结构，不是实际执行证据：

```json
{
  "protocol_version": "0.1",
  "run_id": "example-run-001",
  "status": "success",
  "message": "报表生成完成",
  "result": {
    "report_name": "daily-report.xlsx",
    "processed_rows": 500
  },
  "error": null
}
```

失败示例：

```json
{
  "protocol_version": "0.1",
  "run_id": "example-run-002",
  "status": "failed",
  "message": "浏览器登录状态失效，未完成本轮采集",
  "result": {
    "completed_steps": ["检查本地配置"],
    "failed_step": "访问数据页面"
  },
  "error": {
    "code": "LOGIN_REQUIRED",
    "details": "需要维护人员恢复登录后决定是否重跑"
  }
}
```

示例中的文件名是业务说明，不表示文件已上传中台或可点击下载。结果附件的上传、保存、下载权限与保留期尚待确认。

失败的 `message`、`result` 及可用诊断应能保存在本轮记录中，并用于生成钉钉失败通知。敏感内容需在上报前脱敏；中台发送前再次检查。超长结果的摘要、截断提示和详细记录入口应有一致规则，具体容量与格式待设计，不能静默丢弃失败返回值。

## 5 业务结果与进程状态的判定

建议正常成功退出码为 `0`，业务失败使用非零退出码。执行端需同时核对最终结果、进程状态和本轮标识，不使用单一退出码替代业务约定。

| 观察到的情况 | 建议平台处理 |
| --- | --- |
| 有合法 `success` 结果，进程正常退出且清理已完成 | 确认本轮成功；按任务配置决定是否通知 |
| 有合法 `failed` 结果，进程非零退出 | 记录业务失败并通知，保留失败返回值 |
| 有合法 `failed` 结果，但退出码为 `0` | 仍记为失败，同时提示脚本退出约定不一致 |
| 返回 `success`，但进程非零退出 | 记录执行异常及结果冲突，不能显示成功 |
| 进程已经退出，但缺少结果、结果格式非法或 `run_id` 不匹配 | 记录结果协议异常，不推测业务成功 |
| 已收到最终结果，但进程或本轮自有子进程仍未结束 | 保持未完成，不能释放电脑给下一任务 |
| 手动停止或运行超时，已确认本轮进程停止 | 分别记录已停止或运行超时，保留已有结果和停止原因 |
| 电脑断线，无法确认进程与结果 | 标记状态待核实，保留最后观测时间，不直接判定失败或补跑 |
| 同一结果被重复提交 | 识别为同一轮结果；不重复生成执行记录或告警事件，渠道发送重试另行记录 |

排队超时属于未开始执行的取消事件，不要求脚本返回结果。暂停后续定时不应被解释为停止当前任务。已确认的停止或超时终态不能被迟到结果直接覆盖；冲突应保留证据，具体事件顺序与裁决方式需在状态机设计中确定。

## 6 停止、超时与资源所有权

脚本应可靠释放自己创建的文件、连接、会话、浏览器和子进程。最长运行时间覆盖本轮业务执行与结束清理；建议从执行端确认启动时开始计算，不把排队时长混入运行时长。

接入时区分两种浏览器或应用使用方式：

- **本轮自己启动**：记录资源归属，正常结束或停止时关闭本轮自有资源，不能仅退出入口进程而留下后台任务继续执行。
- **连接既有应用**：说明所连接的实例和使用前提，结束时释放本轮连接；未经明确所有权约定，不得按进程名批量关闭浏览器或其他应用。

停止请求、实际停止和资源清理是不同状态。执行端应先请求有界清理，再按技术方案处理未退出的自有进程；无法确认停止时保持异常占用并通知维护人，不能为推进队列直接启动下一任务。清理等待时长及强制终止边界需经实际 Windows 和浏览器场景验证后确定。

脚本被终止并不代表已撤销写入数仓、接口调用或生成文件等业务副作用。维护人员应说明部分完成结果、幂等处理及恢复办法；平台不能凭一次重跑自动实现业务回滚。

浏览器可启动不等于网站已经登录。已有登录状态的保存位置与访问权限需按任务管理，不放进结果或日志。扫码、验证码和登录失效后的人工恢复流程尚待确认，本规范不承诺自动解决。

## 7 日志、步骤、断线与重跑

- 日志应能够关联本轮任务，记录关键步骤、耗时和失败原因；不记录账号密码、Token、Cookie、Webhook、未脱敏数据或完整敏感响应。
- 可选步骤仅用于说明“正在抓取”“正在处理文件”等当前阶段；不报步骤也不能影响结果交付。步骤不等于最终结果，不能由“最后一步”自动推断成功。
- 中台负责发送钉钉通知，脚本不持有钉钉机器人 Webhook，不各自维护独立通知逻辑。成功通知默认关闭时，不发送成功摘要。
- 网络中断时，执行端需保留本轮标识、状态变化和未确认结果；重连后补传并核对，中台根据同一轮标识去重。缓存容量、保留时间和失败恢复方式待技术设计。
- 结果上报重试、钉钉发送重试与业务脚本重跑是三种不同动作。前两者不应触发业务重复执行；脚本失败第一版按记录和通知处理，不默认自动重跑。
- 脚本自己的外部接口重试需有次数和超时上限，并验证重复请求的业务影响。涉及重跑的任务应说明是否适用补跑；实时数据错过后不能默认按当前时间重新抓取并当作历史结果。
- 使用者手动立即运行仍需进入指定电脑的串行调度，不应绕过其他运行任务或未核实的执行占用。

## 8 接入验收清单

以下是完整接入的验收要求，不代表整套中台已经通过验证。M0 已验证的本机子集见 [M0 交付记录](../delivery/2026-11-19-agent-m0/report.md)；涉及集中调度、通知、真实浏览器登录及两台执行机的完整用例仍为**未验证**。使用人工构造或脱敏数据，在隔离执行环境验证。

| 编号 | 场景 | 验收标准 |
| --- | --- | --- |
| SI-01 | 单次执行与集中调度 | 启动一次只执行一轮；旧常驻定时已停用；结束后不会自行再次启动 |
| SI-02 | 指定环境及缺项 | 多 Python 并存时使用指定环境；缺依赖或浏览器组件时给出具体检查结果，不误报可运行 |
| SI-03 | 准备环境 | 未点击准备时不擅自安装；准备后重新检查，失败有原因，不影响其他任务环境 |
| SI-04 | 成功与失败结果 | 成功按业务约定返回；失败返回值可在中台查到并进入脱敏告警；成功通知默认不发送 |
| SI-05 | 结果协议异常 | 无结果、非法 JSON、错误轮次、不支持版本及结果与退出码冲突均不被当作成功 |
| SI-06 | 串行与排队超时 | 同机不同时运行两个任务；等待超时取消本轮并通知，脚本未被启动 |
| SI-07 | 停止与运行超时 | 手动停止及超时停止可追溯；只清理本轮自有资源；未确认停止时不释放执行电脑 |
| SI-08 | 断网与补传 | 断线显示待核实；同轮补传不重复执行业务、不重复生成运行记录或告警事件；不承诺外部渠道消息绝对只出现一次 |
| SI-09 | 浏览器两种使用方式 | 自启动与连接既有应用均有明确退出方式；不误关非本轮拥有的应用 |
| SI-10 | 过程与结果分离 | 不上报步骤也能正确结束；普通日志或最后一步不能伪造最终结果 |
| SI-11 | 部分完成与人工重跑 | 保留已完成业务的说明；按任务判断重跑是否安全，不默认自动补跑实时数据 |
| SI-12 | 敏感信息与通知失败 | 返回值、日志及告警均脱敏；钉钉发送失败可追踪，不修改任务原本的业务结果 |

## 9 待冻结事项与非范围

M0 本机协议已在 [执行端说明](../../apps/agent/README.md) 和契约模块中限定字段、运行标识、结果文件、退出码冲突及停止语义。后续云端开发前仍需冻结：步骤事件格式；上传任务包与版本清单；自动准备环境的组件范围；网络补传、去重和通知重试策略。

需结合使用方确认：各脚本业务成功标准、补跑适用性、登录人工恢复流程、结果文件是否上传及下载、失败信息可公开到钉钉的范围。统一结构不能代替每个脚本的业务说明。

最初编制本规范时只交付文档。当前 M0 已提供本机 worker、标准库结果 SDK、安装说明和隔离示例；未实现远程执行接口或生产部署，也未改动现有业务脚本、业务环境、真实账号、钉钉或补跑数据。实际接入应继续按 [工程规范](engineering.md) 与 [测试规范](testing.md) 建立验证证据。
