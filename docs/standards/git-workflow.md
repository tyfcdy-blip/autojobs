# Git 协作规范

## 当前仓库状态

模板可在没有 Git 仓库的目录中使用。没有 `.git` 时，“分支、基准提交和差异”应记录为不适用或尚未初始化，不编造提交标识。是否建立仓库、关联远程及设置分支策略由项目所有者决定。

本项目于 2026-11-20 按用户明确要求初始化 Git 并关联 `https://github.com/tyfcdy-blip/autojobs`，使用 `main`，保留远程已有初始提交。此授权用于本次项目导入与推送，不自动授权未来任务的提交、推送或生产部署。

## 修改前后的检查

在已初始化的仓库中，从根目录执行只读检查：

```text
git status --short --branch
git diff --stat
git diff
git diff --cached
git log -1 --oneline
```

编码前识别已有修改及归属。不要覆盖、回退、格式化或删除范围外修改；无法区分归属时停止写入并说明冲突。新增文件应纳入内容检查，`git diff` 不显示未跟踪文件正文，不能把空差异当作全部已审查。

交付前还应检查：

```text
git diff --check
git status --short
```

记录实际基准、变化范围和未跟踪文件；没有真实运行的检查不写“通过”。

## 分支、提交和远程操作

- 沿用仓库已有分支与提交约定；尚无约定时，在首次需要时确定并记录。
- 未经明确授权，不执行 `commit`、`push`、`merge`、`rebase`、`tag`、强推或删除分支。
- 不执行破坏性回退或清理已有修改。回滚应基于可核实的变更与用户授权。
- 自动化测试、初始化和结构检查脚本不得暗中提交、推送、部署或改写历史。
- 批准实施代码不等于批准发布；CI 成功也不等于发布审批。

## 审查材料

一次变更围绕一个可验收目标。说明具体问题、修改后的行为、影响范围、验证证据、未验证项及必要回滚方式。大任务按依赖划分工作包与里程碑，不把无关修改混入。

评审重点包括业务事实、行为兼容、异常路径、测试覆盖、权限和数据风险。L2/L3 保留独立复核证据；AI 复核、人工评审、开发自测、CI 与发布审批分别记录。

本仓库若配置了托管 CI，只有真实远程运行记录才可填“CI 通过”。本地运行相同命令仍属于本地验证。
