# 测试规范

测试由执行任务的 Codex 主导分析、设计、自动化、执行、缺陷定位、修复复验和回归。开发人员补充业务事实、环境和权限，执行无法自动化的人工步骤并作最终确认。没有独立测试岗位不是省略测试的理由。

## 模式和等级

每项任务选择一种模式：全过程开发、开发后自检、独立审查、修复与复验。独立审查默认只读，不把审查授权解释为修改授权。

| 等级 | 最高命中条件 | 最低门禁 |
| --- | --- | --- |
| L1 普通 | 局部修改，不涉核心业务、数据库、公开接口、权限或跨模块调用 | 相关静态/构建检查、单元或模块测试、直接功能验证、必要回归、差异检查与自检 |
| L2 重要 | 业务状态、接口、公共组件、多调用方或跨语言联动 | 实施及测试计划、任务用例追踪、适用单元/API/集成/UI 测试、影响分析、回归及独立复核 |
| L3 高风险 | 权限、金额、财务、订单、库存、审批、数据库、历史数据、并发、外部系统或核心公共能力 | 分阶段实施，适用集成/故障/安全/性能/兼容/恢复/回滚验证，以及人工专项评审 |

同一任务按最高命中等级执行。专项不适用时记录理由，不通过大量无关检查掩盖关键证据不足。模板仓库没有业务构建产物时，可以记录“业务构建不适用”；模板脚本自身仍必须验证。

## 测试计划与用例

使用 [测试计划模板](../templates/test-plan.md)，将每个任务点映射到实现位置、层级、用例和结果。L1 可以将计划、用例和结果合并；L2/L3 需包含范围与排除项、风险、环境、数据、工具、自动化/人工边界、回归范围、准入/退出条件。

按实际边界选择场景：正常、空数据、边界、非法输入、重复、不存在、权限、状态、并发、超时、外部失败、部分失败、历史数据、版本兼容、大数据量和恢复。每个用例记录编号、关联任务、前置条件、输入与步骤、预期、实际证据及状态。

测试数据应可识别、可清理、可重复，不使用未脱敏敏感数据，不污染生产。Mock/Stub 只隔离不可用外部边界，不替换本次核心业务，并说明与真实环境的差异。

## 执行顺序

1. 工作包完成：运行相关静态检查、构建及直接影响的单元/组件/API 测试。
2. 里程碑完成：运行该范围内适用的集成、端到端、异常和回归测试。
3. 全部完成：执行跨里程碑关键链路与最终回归，检查兼容、数据、发布及回滚风险。
4. 已通过后，只在新修改、失败或未解决风险要求时扩大或重复测试。

自动化可行的检查必须执行。无法执行时给出明确环境、输入、步骤与预期结果，并标记“未验证”；环境受限不能推测通过。关键门禁失败时先定位和修复，禁止用未完成工作包宣布里程碑完成。

当前模板可使用：

```text
python scripts/check_project.py
python -m unittest discover -s tests/unit -v
```

命令仅验证模板结构与模板工具，不能证明未来 Java、Vue、Python 业务应用通过。选定业务工具后，把真实可执行命令记录到项目配置和应用 README，沿用其原生测试发现方式。

## 证据与缺陷

报告保存执行时间及时区、运行环境、基准、工作目录、完整命令、退出码、通过/失败/跳过数量、构建结果和证据位置。日志需脱敏；失败运行也要保留。

| 优先级 | 定义 | 处理 |
| --- | --- | --- |
| P0 | 数据丢失、严重安全漏洞、生产不可用、核心结果严重错误 | 阻断，立即说明影响和安全处置 |
| P1 | 明确 Bug、越权、事务/并发错误、接口不兼容或重大回归 | 阻断，修复后复验和回归 |
| P2 | 性能、冗余、维护性、一般兼容或稳定性风险 | 说明影响和处置，评估是否为关键门禁 |
| P3 | 不阻断的改进建议 | 按范围记录，不擅自扩大修改 |

失败测试不得删除、降低断言、扩大跳过或忽略；偶现失败记录条件和风险，不能算作通过。范围外 P0/P1 不擅改，完成安全分析和可执行本地验证后等待决定。

## 完成与质量状态

需求、实现、用例和结果可以互相追溯；关键用例和构建通过；无未关闭 P0/P1；未验证项已披露并符合门禁，才可认为本次任务完成。

L2/L3 需要独立审查代码、用例、覆盖及证据；由独立 agent 完成时如实记录为“AI 独立复核”，不冒充人工评审。未执行则写“独立审查未执行”。

AI 自检：关键证据齐全且无 P0/P1 为“通过”；存在非阻断未验证项、P2 或残余风险为“有条件通过”；存在 P0/P1、关键失败、关键业务未确认或生产影响不明为“不通过/阻断”。

Codex 自检通过不等于开发自测确认、人工代码评审、CI 验证或发布审批通过。这些状态必须分别记录。
