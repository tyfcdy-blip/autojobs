# 技术路线与架构文档任务计划

日期：2026-11-19，Asia/Shanghai。模式：全过程开发（本轮仅调研与文档编制）。等级：L1 文档任务；不实施数据库、并发、权限、外部调用或发布。后续实现这些能力需按实际改动重新定级，不能沿用本次 L1。

## 目标与基准

根据现有 PRD、脚本规范和五张页面原型，推荐一条可维护的首期技术路线，调查 GitHub 高关注项目的可借用能力、许可证和限制，形成技术设计、决策提议和后续验证门禁。没有 Git 仓库，无法提供分支或提交差异；输入及拟更新导航文件的初始 SHA-256 见 [baseline.json](baseline.json)。不覆盖产品事实、不改业务代码或配置、不安装依赖、不接入真实执行电脑或通知渠道。

已知约束：约十几个脚本、两台固定 Windows 10 执行电脑、单机串行、云端 Linux Docker、集中上传与调度、断线可见、业务结果上报、钉钉异常通知。最困难项是交互桌面与浏览器兼容、失联期间的执行确定性和可靠停止。验收证据是可追溯官方来源、需求到设计的映射、故障语义、可执行的后续 POC 验收条件，而非不存在的性能或运行结果。

## 分工与依赖

- 主 agent：组件调研、整体方案、决策记录、导航更新及检查报告；负责核验来源、合并结果和闭环。
- 调度平台调研 agent：仅写 `docs/architecture/research/orchestrators-2026-11-19.md` 及对应 GitHub 快照，比较成品平台，不修改主方案。
- Windows 调研 agent：仅写 `docs/architecture/research/windows-agent-2026-11-19.md` 及对应 GitHub 快照，核验会话、环境、进程和兼容约束。
- 独立复核：方案形成后只读评审，重点检查产品边界、许可证、状态机、Windows 限制及未验证事项；主 agent 核实发现后修订。

两项调研彼此独立；主方案以核验后的事实为输入。文档最终检查依赖全部文件落盘，不把 agent 的结论直接视为产品验证证据。
